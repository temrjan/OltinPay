## Решение D1 — идентичность базы данных → **СНЯТО** (проверено Шагом 0)
Опасение было: новый стек → `oltinpay_db`, а живой демо мог держать `oltinchain_db`
(К-5, 156 МБ) → слепой cutover увёл бы демо на пустую базу. **Факт (read 2026-07-26):
живой контейнер УЖЕ использует `oltinpay_db` и `redis db 3`** — ровно то, что в
новом `.env.example`. Cutover цепляется к **той же** базе и Redis: миграции нет,
потери данных нет. `oltinchain_db` — отдельный старый артефакт (дроп на R-5, К-5),
к живому демо не относится. **D1 закрыт, спец-действий не требует.**

## ⚠️ Решение D3 — role-ключи для нового `.env` (по ревью Гейта-1: мой источник не существует)
Серверной подписью пользуются (grep `Role.*`, проверено): `Role.BANK_OPS` —
`welcome/service.py:81` (welcome-бонус минт), `bank/service.py:195,322` (депозиты,
подтверждение выводов); `Role.RESERVE` — `bank/service.py:77` (аттестации);
`Role.UZS` — `bank/service.py:138` (fx). **Buy/sell и стейкинг серверной подписи НЕ
используют** — они на стороне юзер-кошелька, для них ключи не нужны.

**D3.1 — факт (проверено он-чейн 2026-07-26, не по докам):**
- UZD2 `0x51232fd0…02aA`, `MINTER_ROLE` = `0x9f2df0…56a6`.
- `hasRole(MINTER_ROLE, deployer 0xa3aA356E…069f)` = **true**; `hasRole(DEFAULT_ADMIN,
  deployer)` = **true**. Минтер — деплоер; **отдельного bank-ops EOA не существует**
  (подтверждает `DEPLOYMENTS.md:152`, `v31-money-edge-SPEC.md:61` — вынесено за скоуп V3.1).
- Значит `KEY_BANK_OPS` **заполнить нечем**: P1-B — это `POSTER_ROLE` на Attestor'ах
  (другая роль/контракт, «never transmitted», только 7demo); P1-C — кошельки
  юзеров. Мой прежний «взять из P1-B/P1-C» — **неверен, снят.**

**D3.2 — ИСПОЛНЕНО 2026-07-26 (демо-скоуп: welcome-бонус ВХОДИТ, банк-интеграция НЕТ):**
Cutover сперва поднялся с `KEY_BANK_OPS`=ключ деплоера (b-simple из /check) — Ревьюер
на Гейте-2 обоснованно заблокировал: деплоер держит `DEFAULT_ADMIN_ROLE` (полный контроль),
админ-ключ на публичном API-боксе противоречит нарративу изоляции ключей. **Ротировано
на вариант (a):** сгенерирован bank-ops EOA `0x6d2c91B09bD6b97A46F364951ba4451F1bA551BE`,
деплоер выдал ему `MINTER_ROLE` (tx `0xc66759c331ea…e4bc5`), on-chain подтверждено
`MINTER=true, ADMIN=false`; на сервере `KEY_BANK_OPS`=этот минтер-ключ (проверено:
контейнер деривит в `0x6d2c91B0…`, не в деплоера), рестарт только `oltinpay-api`, без
даунтайма. **Деплоер/админ-ключ на сервере НЕ лежит** — только локально в `contracts/.env`.
`KEY_RESERVE`/`KEY_UZS`/`BANK_HMAC_SECRET` — пустые (банк-интеграцию судьям не показываем).

Исходные варианты (для истории):
- **(a) завести bank-ops минтер:** сгенерировать EOA → деплоер-ключом одна tx
  `UZD2.grantRole(MINTER_ROLE, newEOA)` → приватник в `KEY_BANK_OPS`. Тогда
  welcome-бонус/депозиты работают после cutover. Прецедент есть (так же 3× для
  Attestor `POSTER_ROLE`); газ минта спонсирует paymaster, ETH на EOA не нужен.
  Это отдельная маленькая он-чейн операция (не правка .env), с тем же деплоер-ключом,
  что в К-6 — сам ключ в .env НЕ кладём, кладём приватник свежего EOA.
- **(b) принять безопасный 503:** welcome-бонус и `/bank/*` после cutover отдают
  503 (фикс #34 гарантирует «безопасно», не «работает»), чинить отдельным треком.
- **Решающий факт — что показываем судьям.** welcome-бонус был headline-смоуком Ф1
  (tx `0xb86555c4…`). Если он в демо-сценарии — рек. (a). Если демо = buy/sell/
  переводы/стейкинг/кошелёк без welcome/банка — (b) достаточно, дёшево.
- `KEY_RESERVE`/`KEY_UZS`/`BANK_HMAC_SECRET` — оставить пустыми, **если** демо не
  показывает банк-интеграцию судьям (аттестации/fx/депозиты). Данных о сценарии
  показа у меня нет — к Капитану.

## Runbook cutover (окно простоя — см. Находку #6)
```
# 0. предпосылки: Шаг 0 снят, D1 закрыт, D3 решён, .env готов (см. ниже)
# 1. подготовить /opt/oltinpay — старые контейнеры ЕЩЁ отдают трафик
git -C /opt/oltinpay fetch origin && git -C /opt/oltinpay reset --hard origin/main
#    создать /opt/oltinpay/.env по корневому .env.example; адреса канонические,
#    role-ключи по решению D3; chmod 600 .env
cd /opt/oltinpay && docker compose build          # СБОРКА ВНЕ окна простоя (см. ниже)
# 2. --- начало окна простоя --- погасить два контейнера oltinchain (освободить имена)
cd /opt/oltinchain && docker compose stop oltinpay-api oltinpay-webapp && docker compose rm -f oltinpay-api oltinpay-webapp
# 3. поднять из /opt/oltinpay — БЕЗ --build (образ готов с шага 1); окно закрывается тут
cd /opt/oltinpay && docker compose up -d
#    (compose api command сам делает `alembic upgrade head` до uvicorn)
# 4. независимая проверка (см. ниже)
```
**Почему `build` вынесен из окна (правка по ревью Гейта-1):** `up -d --build`
внутри окна удлиняет простой на время сборки (особенно промах кэша слоёв) — ровно
ту секунду-минуту, которую находка #6 обещает держать короткой. Собираем образ,
пока старые контейнеры ещё живы; в окне остаётся только `up -d`.

## Находка #6 (ЯВНЫЙ пункт) — коллизия имён → окно простоя, без side-by-side
`container_name: oltinpay-api|oltinpay-webapp` жёстко заданы; живые бегут под тем
же именем в проекте `oltinchain`. **Side-by-side подъём невозможен** — Docker не
поднимет второй контейнер с занятым именем. Следствия, вшитые в runbook:
- cutover обязан быть **down (oltinchain) → up (oltinpay-app)** с **окном простоя**
  между шагами 2 и 3 (~секунды–минута); UI на это время отдаёт 502/503.
- откат — **только на локальные образы** (не пересборка): `docker image prune -a`
  запрещён до R-5.
- порядок в runbook (сначала освободить имена, потом поднимать) — не опциональный.

## Находка #7 (ЯВНЫЙ пункт) — индексер стартует сам на boot
`.env.example` пинит `INDEXER_ENABLED=true` (осознанно, R-1…R-3). На старте
нового `oltinpay-api` поднимется поллер (15 с, lookback 5000 блоков, `main.py`) —
**новая движущаяся часть ровно в момент cutover**, в отличие от бота (спрятан за
profile). **Важно (Шаг 0): у живого старого образа индексера НЕТ вообще** — при
cutover он стартует **впервые в проде**, а не «продолжает работать». Решение (D2):
- **(b) `INDEXER_ENABLED=false` в окне, включить после зелёной проверки (рек.):**
  согласуется с собственным принципом проекта «cutover не заводит новых движущихся
  частей» (ровно поэтому бот за profile). Поднять api+webapp, проверить три урла и
  откат, затем флипнуть `true` + рестарт api отдельным проверяемым шагом. Изоляция:
  если индексер закапризничает (RPC/lookback-всплеск), это не спутано с самим cutover.
  Цена: один лишний рестарт.
- (a) принять `true` сразу: проще (на шаг меньше), индексер нужен для демо всё равно;
  минус — новая движущаяся часть впервые стартует прямо в узком окне.
